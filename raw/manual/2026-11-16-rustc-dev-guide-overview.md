More/better compile-time analyses often means the compiler can do better optimizations.\n* Program size: how large is the compiled binary? Similar to the previous point.\n* Compiler compilation speed: how long does it take to compile the compiler? This impacts contributors and compiler maintenance.\n* Implementation complexity: building a compiler is one of the hardest things a person/group can do, and Rust is not a very simple language, so how do we make the compiler’s code base manageable?\n* Compiler correctness: the binaries produced by the compiler should do what the input programs says they do, and should continue to do so despite the tremendous amount of change constantly going on.\n* Integration: a number of other tools need to use the compiler in\n  various ways (e.g.\n\n  ```\n  cargo\n  ```\n\n  ,\n\n  ```\n  clippy\n  ```\n\n  ,\n\n  ```\n  Miri\n  ```\n\n  ) that must be supported.\n* Compiler stability: the compiler should not crash or fail ungracefully on the stable channel.\n* Rust stability: the compiler must respect Rust’s stability guarantees by not breaking programs that previously compiled despite the many changes that are always going on to its implementation.\n* Limitations of other tools:\n\n  ```\n  rustc\n  ```\n\n  uses LLVM in its backend, and LLVM has some strengths we leverage and some aspects we need to work around.\n\nSo, as you continue your journey through the rest of the guide, keep these things in mind. They will often inform decisions that we make.\n\n### Intermediate representations\n\nAs with most compilers,\n\n```\nrustc\n```\n\nuses some intermediate representations (IRs) to\nfacilitate computations.\nIn general, working directly with the source code is extremely inconvenient and error-prone.\nSource code is designed to be human-friendly while at\nthe same time being unambiguous, but it’s less convenient for doing something\nlike, say, type checking.\n\nInstead most compilers, including\n\n```\nrustc\n```\n\n, build some sort of IR out of the\nsource code which is easier to analyze.\n\n```\nrustc\n```\n\nhas a few IRs, each optimized for different purposes:\n\n* Token stream: the lexer produces a stream of tokens directly from the source code. This stream of tokens is easier for the parser to deal with than raw text.\n* Abstract Syntax Tree (\n\n  ```\n  AST\n  ```\n\n  ): the abstract syntax tree is built from the stream of tokens produced by the lexer. It represents pretty much exactly what the user wrote. It helps to do some syntactic sanity checking (e.g. checking that a type is expected where the user wrote one).\n* High-level IR (HIR): This is a sort of desugared\n\n  ```\n  AST\n  ```\n\n  . It’s still close to what the user wrote syntactically, but it includes some implicit things such as some elided lifetimes, etc. This IR is amenable to type checking.\n* Typed\n\n  ```\n  HIR\n  ```\n\n  (THIR) formerly High-level Abstract IR (HAIR): This is an intermediate between\n\n  ```\n  HIR\n  ```\n\n  and MIR. It is like the\n\n  ```\n  HIR\n  ```\n\n  but it is fully typed and a bit more desugared (e.g. method calls and implicit dereferences are made fully explicit). As a result, it is easier to lower to\n\n  ```\n  MIR\n  ```\n\n  from\n\n  ```\n  THIR\n  ```\n\n  than from HIR.\n* Middle-level IR (\n\n  ```\n  MIR\n  ```\n\n  ): This IR is basically a Control-Flow Graph (CFG). A CFG is a type of diagram that shows the basic blocks of a program and how control flow can go between them. Likewise,\n\n  ```\n  MIR\n  ```\n\n  also has a bunch of basic blocks with simple typed statements inside them (e.g. assignment, simple computations, etc) and control flow edges to other basic blocks (e.g., calls, dropping values).\n\n  ```\n  MIR\n  ```\n\n  is used for borrow checking and other important dataflow-based checks, such as checking for uninitialized values. It is also used for a series of optimizations and for constant evaluation (via\n\n  ```\n  Miri\n  ```\n\n  ). This allows us to make sure that identical values (e.g. types in your program) are only allocated once and can be compared cheaply by comparing pointers. Many of the intermediate representations are interned.\n\n### Queries\n\nThe first big implementation choice is Rust’s use of the query system in its compiler. The Rust compiler is not organized as a series of passes over the code which execute sequentially. The Rust compiler does this to make incremental compilation possible – that is, if the user makes a change to their program and recompiles, we want to do as little redundant work as possible to output the new binary.\n\nIn\n\n```\nrustc\n```\n\n, all the major steps above are organized as a bunch of queries that call each other.\nFor example, there is a query to ask for the type of something\nand another to ask for the optimized\n\n```\nMIR\n```\n\nof a function.\nThese queries can call each other and are all tracked through the query system.\nThe results of the queries are cached on disk so that the compiler can tell which queries’ results\nchanged from the last compilation and only redo those.\nThis is how incremental compilation works.\n\nIn principle, for the query-fied steps, we do each of the above for each item individually.\nFor example, we will take the\n\n```\nHIR\n```\n\nfor a function and use queries\nto ask for the\n\n```\nLLVM-IR\n```\n\nfor that HIR.\nThis drives the generation of optimized\n\n```\nMIR\n```\n\n, which drives the borrow checker, which drives the generation of\n\n```\nMIR\n```\n\n, and so on.\n\n… except that this is very over-simplified.\nIn fact, some queries are not\ncached on disk, and some parts of the compiler have to run for all code anyway\nfor correctness even if the code is dead code (e.g. the borrow checker). For\nexample, currently the\n\n```\nmir_borrowck\n```\n\nquery is first executed on all functions\nof a crate.
