This also completes the project goal for this work.\n\nThe never type, spelled\n\n```\n!\n```\n\nin code, is the canonical uninhabited type. It represents the type of diverging computations – computations which never resolve to any value – where any code that follows is unreachable. Expressions that terminate control flow, such as\n\n```\nreturn\n```\n\n,\n\n```\nbreak\n```\n\n, and\n\n```\nstd::process::exit\n```\n\n, also have the type\n\n```\n!\n```\n\n.\n\nSince having a value of the never type is impossible, Rust permits a never-to-any coercion, allowing to turn\n\n```\n!\n```\n\ninto any other type (this is what distinguishes it from any other uninhabited types). This can be used, for example, to not return a value from one of the branches of a\n\n```\nmatch\n```\n\nor an\n\n```\nif\n```\n\n:\n\n```\n```\nfn mrrrow(option: Option<u32>) {\n    let value = match option {\n        // `x` has type `u32`\n        Some(x) => x,\n        // `return` has type `!`, which is then coerced to `u32`,\n        // allowing the `match` to pass type checking.\n        None => return,\n    };\n    // ...\n}\n```\n```\n\nWhile the never type could already be used and observed this way, and even named in the return type of functions (\n\n```\n-> !\n```\n\n), this release allows naming the never type anywhere:\n\n```\n```\nfn infallible_unwrap<T>(res: Result<T, !>) -> T {\n    // ^^ writing `Result<_, !>` was not allowed before\n    let Ok(v) = res;\n    v\n}\n```\n```\n\nAdditionally this release changes\n\n```\nInfallible\n```\n\nto be an alias to the never type. That makes all old APIs that used\n\n```\nInfallible\n```\n\nbe compatible with using\n\n```\n!\n```\n\n. This was the plan ever since the introduction of\n\n```\nInfallible\n```\n\nand is one of the reasons why the never type stabilization was so hard (waffle gave a talk about some of the troubles of the stabilization).\n\nUnfortunately, to allow changing\n\n```\nInfallible\n```\n\n, we had to introduce a breaking change. This release changes the \"never type fallback\" from\n\n```\n()\n```\n\nto\n\n```\n!\n```\n\nin editions before 2024 (i.e. 2015, 2018, and 2021), similarly to what has already been done in edition 2024. This should largely be unnoticeable, but can affect code in some rare cases (for example when ignoring a result of a function returning a generic parameter). Note that this change might also make the compiler detect more code as unreachable.\n\nWe tried to minimize the impact of this breaking change as much as possible, by providing future compatibility warnings far in advance and releasing fixes to public crates that have been broken by this. If a dependency is failing due to issues with the never type, consider updating it, as a fix might have already been released for it.\n\n### ``` Allocator ``` API\n\nThis release brings about the stabilization of the core parts of\n\n```\nallocator_api\n```\n\n, enabling library authors to define custom allocators that can be used together with certain standard library types - currently\n\n```\nVec\n```\n\nand\n\n```\nBox\n```\n\n. This is why we’re introducing\n\n```\ncore::mem::DropGuard\n```\n\n: a new helper type that runs a closure when dropped.\n\n```\nDropGuard\n```\n\ntakes two arguments: a variable and a closure. It implements\n\n```\nDeref\n```\n\nand\n\n```\nDerefMut\n```\n\nso you can keep working with the variable as normal. But when dropped it runs the closure and consumes the variable.\n\n```\nDropGuard\n```\n\nalso implements a\n\n```\ndismiss\n```\n\nassociated function[1] which returns the variable from the guard without running the destructor. This makes it possible to quickly implement all-or-nothing transaction-like APIs with a rollback. Here is an example implementing a parser which uses a guard to roll back mutations in case of failure:\n\n```\n```\nuse std::mem::DropGuard;\nuse std::num::ParseIntError;\n\n/// Attempt to parse all `strings` and push them into `nums`.\n/// If parsing any of them fails, `nums` remains unchanged.\nfn parse_all(nums: &mut Vec<u32>, strings: &[&str]) -> Result<(), ParseIntError> {\n    let len = nums.len();\n    let mut nums = DropGuard::new(nums, move |nums| {\n        nums.truncate(len);    // ← 1. Reset the vec on failure\n    });\n\n    for s in strings {\n        nums.push(s.parse()?); // ← 2. If `?` returns an error, roll back\n    }\n\n    DropGuard::dismiss(nums);  // ← 3. Parsing successful, dismiss the guard\n    Ok(())\n}\n```\n```\n\n### Conjuring zero-sized types\n\nAs Rust's unsafe code guidelines are still being decided, it became clear that it would be very useful to decide what exactly it means to create zero-sized types in an unsafe way, and what we should recommend for people to do this.\n\nThis question is answered in Rust 1.100 with a single function:\n\n```\nstd::mem::conjure_zst\n```\n\n.\n\nInstead of transmuting\n\n```\n()\n```\n\n,\n\n```\nMaybeUninit::uninit().assume_init()\n```\n\n, or various other incantations, this is the dedicated way to create a value of a zero-sized type when you know that doing so is safe to do. If an inhabited type has no size, we know exactly what value it must be: nothing.\n\nOf course, APIs often rely on the inability to construct such types for safety, and that's why this function is unsafe. For example, PyO3's\n\n```\nPython<'py>\n```\n\nis a zero-sized marker token that represents holding the Python GIL (global interpreter lock). At this time, these share a common parent directory.\nDifferent build configurations, like\n\n```\n--features\n```\n\n, can lead to different copies of libraries and binaries in the\n\n```\nbuild-dir\n```\n\n.\nThese copies are kept unique by a build-configuration hash but this hash was not always applied due to platform constraints.\nThis can lead to extra rebuilds, missed rebuilds, confusion over what binaries or libraries are used, and so on.\nThese problems get exacerbated when sharing a\n\n```\nbuild-dir\n```\n\nacross git worktrees.\n\nThe\n\n```\nbuild-dir\n```\n\nnow consistently applies the build-configuration hash to all content by organizing the directories around their build step, rather than their file type, and moving the hash from a file's name to the parent directory.\n\nThis work began with the build directory layout project goal in 2025, and its stabilization is a milestone toward a new project goal, unblocking future improvements such as cache garbage collection, cross-workspace cache de-duplication, cross-workspace caching, and fine grain locking.\n\nWe previously published a call for testing for the changes that are now taking effect. Rust 1.100 stabilizes Cargo's min-publish-age aware dependency resolution, which lets you wait for that window before it picks up newly published versions. Pin a version with\n\n  ```\n  cargo install foo@1.2.3\n  ```\n\n  if needed.\n* Cooldowns reduce the risk from some supply chain attacks but are not a complete defense on their own.
