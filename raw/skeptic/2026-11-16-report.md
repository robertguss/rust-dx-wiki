## Notes on the claims

Formatting: the fetcher puts inline code on separate lines, so quotes that contained inline code (4, 7, 18, 30, 31, 32) were rejoined onto one line. Words are unchanged. "[...]" marks an omission.

Claims that did not survive:

- 6 (outdated). The 2025H2 goal "Production-ready cranelift backend" was closed with no progress because it was not funded. It was replaced by a 2026 goal with a different aim, "Improve `rustc_codegen_cranelift` performance" (status Accepted, "We're targeting a 2x speedup inside the `rustc_codegen_cranelift` backend"). The 2026 Fast Builds roadmap funding table lists it as "✅ | Improve rustc_codegen_cranelift performance | $65,000 | Tweede golf | 🙏 OpenAI, AWS". So a Cranelift goal exists, but it is a performance goal, and nobody is currently promising "production-ready".
- 7 (outdated). I could not fetch a page that states 20% in full. A search snippet of the 2025H2 goals blog post says "offering roughly 20% faster code generation", but the old goal page now only redirects. The newest fetched number is 5% to 12% faster end to end on incremental builds of Zed (February 2026). The two numbers measure different things (code generation alone versus whole incremental build), so the 20% is not shown false, but it overstates what a user sees. The closing comment on goal 397 says the same: "the amount of time spent in codegen for realistic changes to real code bases was smaller than expected".
- 9 (outdated). "Actively maintained" holds (release 0.11.0 on 2026-10-24, pushed today). "Faster than mold" no longer holds without conditions. Mold's own August 2026 benchmarks show Wild "substantially slower than Mold", and Wild's author reproduced part of that gap and attributes it to mold 2.42.0 and 2.42.1 plus benchmark setup (output file on tmpfs, forking). Wild's own charts are SVG images, so no fetched text states Wild's lead in numbers.
- 11 (outdated). Wild now also targets WebAssembly. macOS and Windows are still not supported; they are on the "looking ahead" list. The README does link a "Mac Mini - Mach-O" benchmark page, which suggests Mach-O work is in progress. I did not fetch that page.
- 35 (outdated). I could not find a tool I would call "widely adopted", but the ground is occupied. kache (1,468 stars, created 2026-02-15) and mbx (773 stars, created 2026-08-20, from the author of mise) both exist to share Rust build output across worktrees, and mbx names coding agents in its README. Around them is a crop of small tools built for exactly the parallel-agent case: cargo-reapi (27 stars), cargo-worktree (7), cargo-hauler (6), Cargo Steward (1). "Widely adopted" is a judgment call; by star count these are small next to sccache (7,934).

Confirmed, but about to go stale:

- 8. The stabilization strategy for the parallel front end was accepted as compiler-team MCP 1005 (label `major-change-accepted`, closed, last updated 2026-08-17). Its plan: enable by default on nightly, then "collect user feedback for it for at least ~3 months". The release notes for Rust 1.97.1 through 1.100.0 (2026-11-12) have no parallel front-end entry.
- 12. Relink Don't Rebuild exists on nightly as `-Z public-api-hash`. The 2026 roadmap says "Land in nightly, with limitations | 2026" and "Prepare for stabilization | 2027".
- 16. True only narrowly. rustc already has an in-tree, unstable `-Zllvm-tpde` mode (`RUSTFLAGS="-Zllvm-tpde" cargo +stage1 build`), and there is an accepted 2026 goal to "Distribute the TPDE-llvm library via rustup". Today it needs a locally built compiler and is Linux-only.
- 18. Fine-grain locking is still unstable. A related stabilization (build-dir layout v2) was merged and then reverted on 2026-07-07.
- 21. The Cargo team has an open 2026 goal for a cross-workspace cache with biweekly updates; the latest (2026-11-14) is about getting "cross workspace deduplication into nightly". The parent issue, cargo#5931, has been open since 2018.
- 25. The `target/` GC issue was claimed by a contributor on 2026-08-30, and PR #16929 ("gc: track and clean target directories") is open.

Weaker evidence:

- 4. The source is the pre-release announcement. I did not fetch a current doc restating the default. The 1.99.0 release notes mention a rust-lld fix on macOS, so rust-lld is still shipped.
- 13. Cargo also has an unstable profile setting for it (`-Zprofile-hint-mostly-unused`).
- 22. No page states the negative outright. The evidence is that the request "Support for pre-built dependencies" is still open and labelled `S-needs-design` after eleven years. `cargo-binstall` and `cargo-prebuilt` came up in search but install binaries, not library dependencies.
- 23. kache and mbx both advertise handling "private incremental state" alongside the shared cache, so the sccache limit is no longer a limit of the category. Also, Rust 1.99 release notes: "In Cargo, incremental compilation is now disabled by default when running in CI."
- 24. The Bazel quote is from a 2023 Tweag post, not rules_rust docs. The "Cargo does not do it natively" half rests on the Cargo Book pointing to third-party sccache for sharing.
- 26. The counts are workflow files that mention each action. Hand-rolled `actions/cache` setups for Cargo are not counted, so this shows "most used Rust-specific cache action", which is slightly narrower than the claim.
- 27. The library is framework-neutral, but the same page says "a third-party tool that implements the Subsecond compiler and protocol is required" and suggests the Dioxus CLI, and calls Subsecond "still experimental".
- 30. The doc says the dedicated target dir avoids "locking the Cargo.lock"; the claim says it blocks `cargo build`. Same mechanism, described loosely by the doc.
- 33. The maintainer quote is from May 2025. For today I rely on absence: no repository matching "mcp" in the rust-lang org, no MCP entry on the rust-analyzer configuration page, no "model context protocol" hit in rust-lang/cargo. Absence in search is weaker than a statement.
