Through extensive tracking and the hard work of T-perf and others, performance has gradually improved over the years. However, in practical terms, a 1% improvement here and there is not sufficient to truly improve users’ workflows.\n\nThe cranelift codegen backend (\n\n```\nrustc_codegen_cranelift\n```\n\n) is one of the most concrete ways we have to deliver a serious improvement to compile times in the typical development cycle. This project goal aims to get the\n\n```\nrustc_codegen_cranelift\n```\n\nto a state where we can confidently recommend it for local development.\n\n## Status quo\n\nThe cranelift backend is already very capable, and well-integrated into the rust project. It is able to re-use a lot of infrastructure and code, for instance via\n\n```\nrustc_codegen_ssa\n```\n\n. It can be enabled on a per-project basis in the\n\n```\nCargo.toml\n```\n\n:\n\n```\n```\n# This line needs to come before anything else in Cargo.toml\ncargo-features = [\"codegen-backend\"]\n\n[profile.dev]\ncodegen-backend = \"cranelift\"\n```\n```\n\nIt is however not quite stable and reliable enough for real use. Most large projects run into one or two missing features, meaning that\n\n```\nrustc_codegen_cranelift\n```\n\ncannot be used. Furthermore, small changes in the project and/or its dependencies could run into limitations of\n\n```\nrustc_codegen_cranelift\n```\n\n, so while experimentation with the backend is highly encouraged, we cannot currently recommend it for serious local development.\n\n## The next 6 months\n\nWe plan to work on fixing the following cranelift limitations:\n\n* supporting unwinding (at least on Linux and macOS)\n* fixing remaining ABI issues\n* a better approach for supporting (SIMD) intrinsics\n\nAs a side-effect we will also look at improving code sharing with rustc, for instance by moving more logic into\n\n```\nrustc_codegen_ssa\n```\n\n. These changes reduce the maintenance burden of the other backends (cranelift, but also\n\n```\nrustc_codegen_gcc\n```\n\n), and generally improves the code which is still quite over-fit to LLVM\n\nWith these items completed, we believe that we can confidently recommend the use of the cranelift backend for local development and CI builds on linux and macOS.\n\n### The “shiny future” we are working towards\n\nWe believe we can get to a production-ready\n\n```\nrustc_codegen_cranelift\n```\n\nimplementation for Linux and macOS, on\n\n```\nx86_64\n```\n\nand\n\n```\naarch64\n```\n\n, within the context of this project goal. The problems and solutions are mapped out, and there are many similarities between these targets.\n\nUltimately, we’d like to provide the same level of quality for Windows, but this is much more challenging. Progress on this front is highly dependent on additional funding, and will take considerably more time.\n\nWhile this project aims to deliver a production-ready backend, it is by no means feature-complete at that point. One major missing feature is debug info (i.e. debugger support).\n\nMore long-term we see the cranelift backend as an extremely promising approach for decreasing compile times, and substantially improving developer experience. However, significant technical work remains to be done to achieve that goal.
