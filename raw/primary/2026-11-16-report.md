## Notes and limits

1. **Claim 1:** The 2025 survey results published 2026-03-02 are the latest annual results located. Searches for 2026 results did not locate a newer annual results release. The separate August 2026 target-directory post explicitly describes compilation speed as the most commonly reported problem in that survey: [2026-11-16-target-reduction.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-target-reduction.md).
2. **Claims 2–3:** These are survey respondents’ reported experiences, not a representative measurement of all Rust users. The 45% denominator is respondents who said they no longer use Rust.
3. **Claims 4–5, 8:** Claim 4 applies to the specified GNU/Linux target, starting with Rust 1.90; it is not a statement about all Linux targets. Claims 5 and 8 describe supported toolchain distribution/configuration, not what is possible with a private patched compiler. The fetched build-performance guide supplies the nightly requirements in their respective sections. [2026-11-16-build-performance.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-build-performance.md); [2026-11-16-cranelift-repo.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-cranelift-repo.md).
4. **Claim 6:** The named production-readiness goal belongs to 2025H2; its tracking issue is closed. The current accepted 2026 goal is “Improve rustc_codegen_cranelift performance”, with a backend-internal 2x target and continuing usability work. This is a change in the current goal framing, not evidence that all production-readiness work succeeded. The current tracking issue is open (updated 2026-10-22): [2026-11-16-cranelift-current-status.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-cranelift-current-status.md). An attempted guessed 2026 production-ready URL returned `page_not_found`: [2026-11-16-cranelift-current.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-cranelift-current.md). The old rust-lang.github.io URL returned only a move notice: [2026-11-16-cranelift-goal.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-cranelift-goal.md).
5. **Claim 7:** Confirmed only in the precise sense of the project’s published 2025H2 measurement: about 20% less **code-generation time**, about 5% less total clean-build time. It is not a universal current end-to-end benchmark. The 2026 goal reports a different experiment: Zed incremental totals 5%/12% faster (depending on debug info), and average single-crate speedups around 10–15% with line-tables-only: [2026-11-16-cranelift-2026.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-cranelift-2026.md). These measurements have different scopes and should not be pooled.
6. **Claim 9:** Confirmed as an existence claim about a benchmark, not blanket dominance. The current Wild Zed-debug benchmark SVG labels Mold 3.0.0 at +107% time relative to Wild 0.11.0 at +0%; the table includes the exact SVG text elements. Its prose specifies AMD Ryzen 9 9955HX, 92 GiB RAM, generally tmpfs. Repository metadata reports archived=false and pushed_at=2026-11-16T01:06:20Z: [2026-11-16-wild-metadata.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-wild-metadata.md). Other workloads, versions and filesystems can differ; these are project-maintained benchmarks, not independent reproduction.
7. **Claims 10–11:** The current README explicitly says incremental linking is not implemented. Claim 11 is refuted **as literally worded (“only Linux”)** because the supported-target list also includes WebAssembly. Its narrower macOS/Windows assertion is still supported: Mach-O and Windows are listed under future work. A Mac Mini benchmark link in the README alone does not establish shipped Mach-O support.
8. **Claim 12:** The current 2026 roadmap schedules limited nightly RDR for 2026 and preparation for stabilization for 2027; the older RDR proposal is a design document, not a stable feature announcement. [2026-11-16-relink.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-relink.md).
9. **Claims 13–14:** Both flags are unstable. hint-mostly-unused is explicitly a hint, can make other cases slower, and exempts extern/inline(never) functions. The proc-macro option is for derive invocations, and the docs warn that impure macros can yield stale expansions; this is not a safe general cache for all procedural macros.
10. **Claims 15–16:** The 10–20x number belongs to TPDE-LLVM code generation, not total Rust builds. The paper reports 8–24x for SPECint 2017 LLVM-IR: [2026-11-16-tpde-paper.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-tpde-paper.md). Current rustc docs expose `-Zllvm-tpde` / `-Zllvm-tpde=try`, which fall back to LLVM on unsupported IR, and `=only`, which fails instead. Thus the old blanket “no usable integration” claim is outdated; a complete replacement for LLVM across arbitrary projects is not established. The source still calls it experimental, and this research did not install or benchmark it.
11. **Claims 17–18:** Claim 17 describes normal coarse-locking behavior for commands that build. It should not be read as “every pair of cargo subcommands always blocks”. The experimental tracking issue says only non-artifact-producing commands such as check can currently run in parallel and lists remaining blocking cases: [2026-11-16-locking-issue.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-locking-issue.md).
12. **Claims 19–21:** build.build-dir stabilized in 1.91, while the newer filesystem layout stabilized in 1.100.0 according to the fetched nightly book. Separating intermediate files does not itself create a cross-workspace cache. The accepted cache goal and open tracking issue explicitly distinguish that future cache from manually sharing CARGO_TARGET_DIR. Default independent worktree roots imply independent workspace-local artifact directories. Current cache roadmap: [2026-11-16-cache-issue.md](/home/exedev/code/rust-dx-wiki/raw/primary/2026-11-16-cache-issue.md).
13. **Claim 22 — unverified:** The open pre-built-dependencies request and Cargo source-cache docs support the current source-oriented model, but do not prove the absolute absence of every supported download path for crates.io library artifacts. cargo-binstall installs executable tools, which does not settle this claim.
